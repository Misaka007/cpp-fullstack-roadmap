# C++ 编译器支持与迁移

## 标准模式与能力边界

编译选项只选择语言标准模式，不保证该标准的所有语言特性、标准库组件、调试器和构建工具都已经可用。迁移时应以目标平台上的实际编译与测试结果为准。

| 工具链 | 常用标准选项 | 工程建议 |
| --- | --- | --- |
| GCC | `-std=c++11` 至 `-std=c++23` | 固定最低版本，并将警告与标准模式写入构建系统 |
| Clang | `-std=c++11` 至 `-std=c++23` | 同时确认使用的标准库是 libc++ 还是 libstdc++ |
| MSVC | `/std:c++14`、`/std:c++17`、`/std:c++20`、`/std:c++latest` | 将 `/Zc:__cplusplus` 纳入兼容配置，避免读取到历史值 |
| CMake | `CXX_STANDARD` 或 `target_compile_features` | 优先按 target 声明能力，避免全局编译选项泄漏 |

```cmake
add_library(net_core net_core.cpp)

# 接口要求：依赖此库的目标需要至少具备 C++20。
target_compile_features(net_core PUBLIC cxx_std_20)
set_target_properties(net_core PROPERTIES CXX_EXTENSIONS OFF)
```

- `CXX_STANDARD` 表达期望版本；`target_compile_features` 更适合库的公开最低要求，并能由 CMake 选择相应选项。
- 不使用 `-std=gnu++20` 等 GNU 扩展模式作为可移植接口前提；若确实依赖扩展，应明确隔离。
- MSVC 传统上可能把 `__cplusplus` 报告为旧值；检测语言版本时需启用 `/Zc:__cplusplus`，或优先检查具体特性宏。

## 特性检测与降级

```cpp
#if defined(__cpp_lib_expected) && __cpp_lib_expected >= 202202L
#include <expected>
using PortResult = std::expected<int, ParseError>;
#else
// 兼容层：在项目内部使用等价 Result 类型，保持对外 API 稳定。
using PortResult = Result<int, ParseError>;
#endif
```

| 检测方式 | 用途 | 局限 |
| --- | --- | --- |
| `__cplusplus` | 粗略判断语言模式 | 不能判断单个库特性是否实现 |
| `_MSVC_LANG` | MSVC 下的语言模式辅助判断 | 仅适用于 MSVC 生态 |
| `__cpp_*` | 检测语言特性 | 宏值和可用性必须与标准要求一起判断 |
| `__cpp_lib_*` | 检测标准库特性 | 需要包含对应头文件后才可能定义 |
| `__has_include` | 检查头文件是否存在 | 头文件存在不代表 API 完整可用 |

- 先检测“所需的具体能力”，再提供兼容实现或关闭可选功能；不要仅通过 GCC/Clang/MSVC 的品牌和版本号猜测支持情况。
- 区分语言前端支持与标准库支持：编译器可能支持协程语法，但所需的 `<format>`、时区数据库或并发库组件仍缺失或不完整。
- C++ 模块、协程、栈踪迹等还会受构建器、链接器、符号文件和运行时影响，最小编译通过不等于产品可用。

## 多平台验证与 ABI

```text
pull request
     |
     +--> GCC + libstdc++  : C++20 / C++23
     +--> Clang + libc++   : C++20 / C++23
     +--> MSVC             : C++20 / latest
     |
     +--> unit tests + sanitizer + public-header compile test
```

| 验证项 | 目的 | 常见遗漏 |
| --- | --- | --- |
| 多编译器矩阵 | 捕捉扩展和实现差异 | 只在开发机 GCC 上通过 |
| 多标准矩阵 | 验证最低标准承诺 | 升级后意外使用更高版本 API |
| 公共头编译测试 | 验证宏、包含顺序和 API | 仅编译库自身源文件 |
| ABI 检查 | 防止二进制接口不兼容 | 混用不同编译器、运行库或 C++ ABI 选项 |
| Sanitizer | 发现未定义行为和资源问题 | 只跑 release 配置 |

- 不应混用不同主版本工具链编译出的 C++ 二进制接口，除非平台、运行库和 ABI 兼容性已被供应方明确保证。
- GCC 的 `_GLIBCXX_USE_CXX11_ABI` 会影响部分标准库类型的二进制布局与符号名；同一进程内交互的库应保持一致，不能把它当作任意兼容开关。
- 对外发布 C++ ABI 时，尽量使用 PImpl、稳定的 C 接口或序列化边界，避免在 ABI 中暴露 `std::string`、`std::vector` 和模板实现细节。

### 缺失知识点与工程注意事项

- 不要把 `__cplusplus >= 202002L` 当作标准库功能可用的充分条件；需要 `<version>` 或相应头文件中的库特性宏。
- 功能宏只回答“实现宣称支持什么”，仍要编译最小示例并覆盖目标操作系统、架构、标准库和发布配置。
- 使用 `std::filesystem`、`std::thread`、`std::format` 等组件时，链接要求可能随工具链时代变化；构建脚本应显式声明依赖。
- `CMAKE_CXX_STANDARD` 是目录级默认值，第三方子项目可能覆盖它；对关键 target 设置明确的编译特性。
- 将“最低支持版本”“已验证组合”“废弃计划”写入项目文档和 CI 配置，避免口头约定失效。

### 代码注释提示

```cpp
// 可移植性：检测具体库特性宏，而不是猜测某个编译器版本。
// API 稳定性：公开接口避免暴露与标准库 ABI 强绑定的实现类型。
// 降级路径：新特性不可用时保持语义等价，而非静默删除错误处理。
// 构建边界：目标声明最低语言标准，依赖者可在配置阶段尽早失败。
```

### 可能的面试题

- **问题：** 为什么项目启用 C++20 后，仍可能无法使用某个 C++20 标准库组件？
- **简要答案：** 标准模式主要控制语言规则，标准库由具体工具链版本实现；某些组件还依赖运行库、系统时区数据、链接器或调试符号。因此应检测对应的 `__cpp_lib_*` 宏，并在目标 CI 环境编译和测试。

- **问题：** 如何降低 C++ 动态库升级的 ABI 风险？
- **简要答案：** 固定并验证工具链和运行库组合；公开边界使用 PImpl、C ABI 或稳定的数据格式；不要直接暴露容易随标准库或编译器变化的模板与标准容器实现类型。
