# 现代 C++ 特性组合与避坑

单个新特性通常不难，难点在于组合时仍能保持所有权明确、生命周期安全、错误可处理和接口稳定。本章以常见工程问题为入口说明如何选型。

## 资源管理：RAII、值语义与 Rule of Zero

```cpp
class Socket {
public:
    explicit Socket(int fd) noexcept : fd_(fd) {}
    ~Socket() { if (fd_ >= 0) ::close(fd_); }

    Socket(const Socket&) = delete;
    Socket& operator=(const Socket&) = delete;

    Socket(Socket&& other) noexcept : fd_(std::exchange(other.fd_, -1)) {}
    Socket& operator=(Socket&& other) noexcept {
        if (this != &other) {
            if (fd_ >= 0) ::close(fd_);
            fd_ = std::exchange(other.fd_, -1);
        }
        return *this;
    }

private:
    int fd_ = -1;
};

struct Session {
    // Rule of Zero：成员自己管理资源，Session 无需手写析构、拷贝或移动函数。
    std::unique_ptr<Socket> socket;
    std::string user;
};
```

| 问题 | 推荐组合 | 原因 | 常见误用 |
| --- | --- | --- | --- |
| 独占文件、socket、锁 | RAII 包装器 + `noexcept` 移动 | 离开作用域自动释放，容器可高效迁移 | 裸句柄分散在多个函数中手工关闭 |
| 多态对象所有权 | `unique_ptr<Base>` + 虚析构函数 | 所有权唯一且支持运行时多态 | 用 `shared_ptr` 只是为了省去思考所有权 |
| 共享观察 | `shared_ptr` + `weak_ptr` | `weak_ptr` 不延长生命周期，可打破环 | `shared_ptr` 相互引用造成泄漏 |
| 只读借用 | `const T&`、`string_view`、`span` | 避免不必要复制 | 保存 view/reference 到源对象销毁之后 |

- Rule of Zero：优先使用 `std::string`、容器、智能指针和 RAII 成员，让编译器生成特殊成员函数。
- 只有类直接拥有非 RAII 资源时才考虑 Rule of Five；此时必须同时推导析构、拷贝和移动语义，不能只补一个析构函数。
- 多态基类如果可能通过基类指针销毁，析构函数应为 `virtual`；不允许多态删除时可显式 `protected` 非虚析构来表达约束。

## 生命周期：视图、Lambda 与异步任务

```cpp
std::function<void()> make_bad_task() {
    std::string message = "done";
    return [&message] { std::cout << message; };  // 错误：返回后 message 已销毁。
}

auto make_task(std::string message) {
    return [message = std::move(message)] {
        std::cout << message;  // 闭包拥有 message，任务可安全延后执行。
    };
}

std::string_view bad_prefix() {
    return std::string("prefix").substr(0, 3);  // 错误：view 指向临时字符串。
}
```

| 对象/特性 | 是否拥有数据 | 安全使用方式 | 高发问题 |
| --- | --- | --- | --- |
| `std::string` / `vector` | 是 | 跨异步边界按值保存或移动 | 拷贝成本未评估 |
| `string_view` / `span` | 否 | 仅在底层数据稳定且存活期间使用 | 指向临时对象、扩容后继续使用 |
| Lambda `[&]` | 否，借用外部对象 | 同步、短作用域调用 | 投递线程池后引用悬空 |
| Lambda `[x = std::move(x)]` | 通常是 | 任务独占资源 | 闭包不可复制但队列要求复制 |
| `this` 捕获 | 否，只复制指针 | 用 `shared_from_this()` 或外部生命周期协议 | 对象销毁后回调仍执行 |

- `std::function` 需要可复制目标；持有 `unique_ptr` 的 Lambda 可用模板回调、移动任务队列或 C++23 的 `std::move_only_function`。
- 使用 `shared_from_this()` 前对象必须已由 `shared_ptr` 管理；构造函数中调用它会抛出 `bad_weak_ptr`。
- `[*this]` 是按值复制对象，不是延长原对象生命周期；它只适用于对象可复制且需要快照语义的场景。

## 错误处理：异常、optional 与 expected

```cpp
enum class ParseError { empty, invalid, out_of_range };

std::expected<int, ParseError> parse_port(std::string_view text) {
    if (text.empty()) return std::unexpected(ParseError::empty);
    int port{};
    const auto [end, ec] = std::from_chars(text.data(), text.data() + text.size(), port);
    if (ec == std::errc::result_out_of_range) return std::unexpected(ParseError::out_of_range);
    if (ec != std::errc{} || end != text.data() + text.size()) return std::unexpected(ParseError::invalid);
    return port;
}
```

| 情况 | 推荐类型 | 调用方形态 | 不宜使用 |
| --- | --- | --- | --- |
| 查无此项属于正常结果 | `optional<T>` | `if (value) ...` | 需要区分失败原因时 |
| 可预期且需反馈原因的失败 | `expected<T, E>` | 值/错误显式分支 | 极低层、无法合理构造错误对象时 |
| 跨多层、当前层无法恢复的失败 | 异常 | 在边界统一捕获 | 高频正常控制流 |
| 调用者无需结果 | `void` 或错误码 | 明确记录/处理副作用 | 静默吞掉失败 |

- 一个接口尽量确定一种主错误模型；不要在同一层同时返回 `optional`、错误码并抛异常。
- `noexcept` 不是“性能优化开关”：异常从 `noexcept` 函数逸出会调用 `std::terminate`。仅在确实不抛或必须终止的边界使用。
- C API、线程入口、析构函数和 `extern "C"` 回调是常见异常边界，应捕获并转换异常，避免跨越不支持异常的边界。

## 泛型：从类型推导到 Concepts

```cpp
template <class T>
concept SortableRange = std::ranges::random_access_range<T> &&
                        std::sortable<std::ranges::iterator_t<T>>;

template <SortableRange Range>
void sort_scores(Range& scores) {
    std::ranges::sort(scores);
}

template <class T>
decltype(auto) front(T&& range) {
    // 转发：保持传入范围的值类别；调用方仍要保证返回引用不悬空。
    return *std::forward<T>(range).begin();
}
```

| 需求 | C++11/14 方法 | C++17 方法 | C++20 方法 |
| --- | --- | --- | --- |
| 类型分支 | SFINAE、`enable_if` | `if constexpr` | `requires` / Concepts |
| 通用回调 | 函数模板 | 泛型 Lambda | 受约束泛型 Lambda |
| 序列处理 | iterator pair + 算法 | 同左 | ranges + views |
| 保留值类别 | 转发引用 + `forward` | 同左 | 同左，concept 约束接口 |

- `T&&` 只有在“类型由推导得到的模板参数”场景才是转发引用；例如 `void f(Widget&&)` 只是右值引用。
- 公开泛型 API 应使用 Concepts 描述真正的操作需求，例如可排序、可调用、可迭代，而不是仅约束为某个容器类型。
- `decltype(auto)` 适合包装器精确保留返回类型；普通局部变量通常用 `auto`，可读性更好且不易意外返回引用。

## 并发：从互斥到可停止任务

```cpp
class Queue {
public:
    std::optional<Job> pop(std::stop_token stop) {
        std::unique_lock lock(mutex_);
        // 停止回调会唤醒 condition_variable_any，避免仅请求停止却永久阻塞。
        if (!cv_.wait(lock, stop, [&] { return !jobs_.empty(); })) return std::nullopt;
        Job job = std::move(jobs_.front());
        jobs_.pop();
        return job;
    }

private:
    std::mutex mutex_;
    std::condition_variable_any cv_;
    std::queue<Job> jobs_;
};
```

| 需求 | 首选工具 | 关键不变量 | 易错点 |
| --- | --- | --- | --- |
| 保护复合共享状态 | `mutex` + RAII 锁 | 所有访问由同一把锁保护 | 原子变量和普通变量混用却无同步 |
| 等待状态变化 | `condition_variable` + 谓词 | 谓词、状态与锁配套 | 忽略伪唤醒或丢失通知 |
| 简单计数/标志 | `atomic` | 内存序与状态转移正确 | 以为多个原子自然组成事务 |
| 生命周期受控的线程 | `jthread` + `stop_token` | 循环和阻塞点响应停止 | 只请求停止却没有唤醒阻塞线程 |
| 多锁协作 | `scoped_lock` | 锁顺序由统一机制处理 | 持锁调用外部回调导致重入死锁 |

- 数据竞争是未定义行为；“偶尔看起来正常”不说明代码正确。
- `volatile` 不是线程同步工具，不能替代 `atomic` 或锁。
- 先使用锁得到正确性，再根据性能剖析决定是否需要无锁设计；无锁算法需要处理 ABA、内存回收和内存序。

### 缺失知识点与工程注意事项

- 传值、`const&`、`&&` 的选择应表达所有权和成本：需要保存或异步使用时按值接收再移动通常更安全。
- 用 sanitizer 验证假设：ASan/UBSan 查内存和未定义行为，TSan 查数据竞争；它们不能替代代码审查与压力测试。
- 不要为了“零成本抽象”牺牲可读性。先写清晰的 RAII 和算法代码，再用基准测试定位瓶颈。
- 公共库头文件避免暴露难以稳定的模板实现、第三方类型和依赖具体标准库 ABI 的细节。

### 可能的面试题

- **问题：** 为什么在异步任务中按引用捕获通常危险？
- **简要答案：** Lambda 可能在创建它的作用域结束后才执行，而按引用捕获的局部对象已经销毁，访问将产生悬空引用。对于任务需要的数据，应按值捕获或用初始化捕获转移所有权；共享对象则要有明确的生命周期协议。

- **问题：** 原子变量能否替代互斥量？
- **简要答案：** 只能覆盖少量独立状态，如计数或标志。多个变量共同维持的不变量、复杂读改写和条件等待通常需要 mutex；原子操作若内存序或状态机设计错误，同样会出现并发 bug。
