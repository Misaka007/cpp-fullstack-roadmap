## 二、具体实现

```cpp
#include<iostream>
using namespace std;

class Subject{   //卖书的接口
    public:
        virtual void sailbook() = 0;
    private:
};

class RealBook : public Subject{  //实体店卖书
    public:
        virtual void sailbook(){
            cout<<"卖书"<<endl;
        }   
    private:
};
//a中包含b类;
//让代理类(Dangdang)包含了一个书店(RealBook),代理和书店都实现了一个协议
class Dangdang : public Subject{  //网上卖书
    public:
        virtual void sailbook(){
            RealBook *rsb = new RealBook;
            rsb->sailbook();
            discount();
        }   
    public:
        void discount(){
            cout<<"双十一打折"<<endl;
        }
    private:
        Subject *m_subject;
};

int main(void){
    Subject *s = new Dangdang;
    s->sailbook();

    delete s;

    return 0;
}
```

## 三、桥接模式

**将抽象部分和实现部分进行分离；**

外观模式：客户要使用N个功能,N个功能又相似,就可以抽象起来；

享元模式：有一个对象可能使用1000次,怎样避免对这些对象进行重复的创建呢?避免对象的大量创建!

## 补充：代理与桥接的分界

| 模式 | 主要意图 | 典型场景 |
| --- | --- | --- |
| 代理 | 控制对同一对象接口的访问 | 缓存、鉴权、远程调用、延迟加载 |
| 桥接 | 将抽象与实现独立演进 | 多平台渲染、多个设备/协议实现 |
| 适配器 | 转换不兼容接口 | 接入遗留库或第三方接口 |

- 代理与被代理对象通常实现相同接口；桥接的抽象层持有实现层接口，两侧可分别扩展。
- 远程代理需要补充超时、重试、幂等性和序列化错误处理，不能仅把本地调用包装成类。
- 桥接层级过多会降低可读性；只有抽象和实现确实独立变化时才值得拆分。

## 面试辅导

### 面试考点全景图

| 维度 | 回答要点 | 面试高频追问 |
| --- | --- | --- |
| 核心定义 | `代理与桥接` 属于设计模式，重点是以稳定抽象隔离变化的对象协作方案。 | 它解决了什么问题，边界在哪里？ |
| 关键角色 | 抽象接口、具体实现、客户端、组合关系。 | 各角色的职责、依赖方向和生命周期是什么？ |
| 优点 | 通过清晰边界降低耦合，并让复杂度、资源或并发控制可被推理。 | 性能收益是否可量化？ |
| 代价 | 会引入额外抽象、状态管理或运行时/维护成本。 | 何时不应使用？ |
| 适用场景 | 需求满足本节的约束，并且需要明确演进、资源或并发边界时。 | 如何在现有工程中渐进式落地？ |

### 面试官追问链

1. **基础：** 请定义 `代理与桥接`，并用本节示例说明它解决的实际问题。
2. **机制：** 从意图、参与者、协作关系和扩展代价说明模式；关键对象、调用顺序或数据流是什么？
3. **深入：** 与相邻设计模式相比，变化点位置、对象创建方式、组合关系和耦合方向有什么取舍？
4. **工程：** 出现异常、资源不足、并发竞争或输入非法时如何保证正确性？
5. **优化：** 在基准数据明确后，如何定位瓶颈并以复杂度、延迟或内存指标验证优化？

### 横向对比

| 对比项 | `代理与桥接` | 相邻设计模式 | 选择建议 |
| --- | --- | --- | --- |
| 核心目标 | 以稳定抽象隔离变化的对象协作方案 | 解决相邻但边界不同的问题 | 先按问题边界选择，不按名词选择。 |
| 主要成本 | 抽象、状态与维护成本 | 成本模型不同，可能偏向性能或灵活性 | 用实际负载和团队维护能力评估。 |
| 适用条件 | 需要从意图、参与者、协作关系和扩展代价说明模式 | 需要不同的数据流、生命周期或调用方式 | 不能同时满足时，优先保证正确性与可观测性。 |

### 容易忽略的知识点

- 模式不是目的；警惕为了模式增加层级、全局状态、隐式依赖或不必要的虚调用。
- 面试回答要区分**语言/库的保证**与**当前实现的经验行为**，避免把未定义行为或实现细节当作标准。
- 先说明前置条件和失败路径；“能跑”不是工程正确性，资源回收、日志和测试同样是答案的一部分。
